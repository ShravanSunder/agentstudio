# Pane Zoom

## Product promise

Pane Zoom temporarily expands one durable terminal pane in its tab. It may show
that terminal beside one retained Files/Review Viewer companion without changing
the tab's durable arrangement.

Pane Zoom is a runtime presentation, not an arrangement. The feature is named
Pane Zoom or Zoom in user-facing UI; `Focus` remains reserved for keyboard and
pane-focus concepts.

## Ownership map

```text
durable arrangement
  owns: pane membership, geometry, minimization, persistence
  remains unchanged underneath Zoom

WorkspacePanePresentationAtom
  owns: per-tab runtime Zoom value state and per-source companion metadata

PaneTabViewController
  owns: command capability, target resolution, and dispatch

WorkspaceSurfaceCoordinator + existing view registry
  own: retained companion lifecycle and mounted resources

ZoomPresentationContainer
  owns: one parent toolbar and source/Viewer composition
```

The companion never enters durable pane membership, arrangement membership,
persistence, ordinary Viewer reuse, or IPC enumeration.

## Command contract

### Zoom Pane

- `zoomPane` is available only for durable terminal main panes.
- It enters, cancels, retargets, or resumes the active tab's Zoom presentation.
- Webview, Bridge Viewer, Code Viewer, unsupported panes, and drawer children
  cannot Zoom.
- Runtime execution validates the same capability for toolbar, command bar,
  shortcuts, targeted dispatch, and IPC.

### Viewer

- `showViewer` is valid only for the source terminal of the active tab's Zoom.
- It toggles or retries that source's retained Zoom Viewer companion.
- It is contextual-only in the command catalog, with no pane/worktree target
  rows and no durable fallback.
- Existing durable `showBridgeReview`, `showBridgeFiles`,
  `openBridgeReviewInNewTab`, and `openBridgeFilesInNewTab` commands remain
  separate.
- Zoom without a resolvable worktree remains valid; Viewer is visible-disabled.
- Command visibility may use
  `FocusRequirement.hasActiveTerminalZoom` in the current command system.
  Runtime `canExecute` and the narrow Zoom Viewer capability resolver remain
  authoritative.

The later CommandContext restoration is a separate PR. Pane Zoom must not add a
`ZoomSurface`, rename current command-context types, or broaden the command
system.

## Runtime behavior

- Each tab retains an independent Zoom presentation.
- Switching tabs suspends Zoom visually; returning restores it.
- Retargeting terminal A to terminal B retains A's companion loaded-hidden.
- Two source panes for the same worktree retain separate companion identities.
- First companion creation is visible and opens Files.
- Files/Review switching stays inside the Viewer.
- Cancel reveals the unchanged durable arrangement.
- Companions survive hide, cancel, retarget, and tab switching.
- Companions retire at source, tab, workspace, and application terminal
  lifecycle boundaries. Invalid-resource recovery also clears stale companion
  ownership when its host/runtime is already lost or its source worktree
  identity no longer matches; Zoom remains active with Viewer retryable or
  unavailable.
- BridgeWeb, Bridge protocol, worker, transport, construction identity, Git
  policy, foreground-admission policy, and Bridge activity truth tables remain
  unchanged.

## Toolbar contract

```text
Normal terminal

[icon] Zoom │ [Drawer Toggle] [Add Drawer]
              …space… [Editor] [Finder] │ [Inbox]

Zoomed terminal

[selected icon] Zoom [Viewer] │ [Drawer Toggle] [Add Drawer]
                                      …space… [Editor] [Finder] │ [Inbox]
```

- Zoom uses an icon and visible `Zoom` text.
- Viewer appears only in terminal Zoom.
- One Zoom-wide parent Drawer toolbar is shown.
- Source and Viewer children use typed hidden pane toolbars.
- Drawer Toggle and Add Drawer are adjacent with no separator between them.
- One separator follows the pane-mode group.
- One separator precedes Inbox.
- Empty separators are forbidden.
- All icon-only buttons use one square hit target, frame, alignment, hover fill,
  selected fill, intra-group spacing token, and separator-padding token.
- SF Symbol optical differences must not change layout spacing.
- Every control projects a typed `AppCommandSpec`, `LocalActionSpec`, or typed
  descriptor.
- Every dense toolbar control participates in the shared floating tooltip
  anchor and native control help.
- Arrangement creation also uses the typed tooltip system.
- Copy UI is not part of this change.

## Arrangements

```text
ARRANGEMENTS
[Default] [Layout 1] [Layout 2] [+ disabled]

────────────────────────────────────────
PANE ZOOM
[Zoom Pane selected]  repo / worktree
                      useful relative CWD
```

- The Pane Zoom section appears only while Zoom is active.
- It shows stable source identity with full-path tooltip/accessibility help.
- Pane Visibility is hidden during Zoom.
- Durable arrangement selection, traversal, rename, and delete remain enabled.
- Selecting or traversing a durable arrangement cancels Zoom and selects it.
- Arrangement creation stays visible but disabled.
- Execution also rejects arrangement creation and pane-visibility mutation
  during Zoom.
- The arrangement trigger reads `Zoom Pane` while Zoom is active.

Default remains visibility-complete. Rearranging or resizing Default does not
create a layout. The first deliberate hide/minimize from Default atomically
creates `Layout N` and hides there. Management reveals minimized panes for
recovery; there is no user-controlled `showsMinimizedPanes`.

## Management chrome

Normal panes include Open Arrangements in the existing top-left management
cluster.

Zoom owns one parent cluster:

```text
[Cancel Zoom: xmark.circle] [Open Arrangements]       ZOOM PANE
```

The source ordinal is preserved. The `ZOOM PANE` pill is loud and
non-draggable. Zoom hides Minimize, Close, rearrangement, add-main-pane, and
browser controls while preserving source Drawer controls and drawer contents.
No other Zoom-specific management controls are added.

## Programmatic proof surface

- Authenticated `command.execute` may invoke `zoomPane` only for a durable pane
  target and requires the existing `appCommandExecute` and `layoutMutate`
  privileges.
- Authenticated `ui.arrangements.open` opens the Arrangements panel, accepts
  only an optional durable pane target, and requires the existing `uiPresent`
  privilege.
- Runtime Zoom companions are never valid IPC targets or query results.
- Debug-token escrow may grant these existing privileges only in an opt-in
  debug launch so the native proof journey can authenticate. Stable and beta
  channels ignore debug escrow, and unsafe no-auth execution remains denied for
  both methods.
- No Bridge IPC method, privilege class, or unsafe bypass is added.

## Proof obligations

- Unit capability matrices cover terminal/non-terminal, main/drawer,
  active/inactive tab, enter/cancel/retarget/resume, and stale targets.
- Command tests prove `showViewer` has no durable fallback.
- Visibility tests cover `hasActiveTerminalZoom`.
- Toolbar tests cover state, order, frames, spacing, separators, and typed
  tooltips.
- Arrangement tests cover presentation and execution-level rejection.
- Lifecycle integration uses semantic barriers rather than wall-clock sleeps.
- Real SQLite proof excludes Zoom and companions from persistence.
- Existing Bridge activity truth-table tests remain unchanged and green.
- A debug app is inspected for normal terminal, Zoom Viewer hidden/visible,
  Arrangements, and Management. Screenshot review checks every icon frame, gap,
  separator, label, tooltip, and child-toolbar absence.

## Non-goals

- CommandContext restoration.
- A new command-surface framework.
- Zoom for non-terminal panes.
- BridgeWeb or Bridge protocol changes.
- Copy menu implementation.
- A generic toolbar framework.
