1.3 Q2 — How the browser sends `stream.frameObserved` [VERIFIED]
--------------------------------------------------------------------------------

Sender: BridgeWeb/src/core/comm-worker/bridge-product-transport.ts:665-709
  #acknowledgeMetadataFrame  (:665-681)  and  #acknowledgeContentFrame (:683-698)
  both build `{kind:'stream.frameObserved', ...}` and call #sendFrameAcknowledgement (:700-709).

Transport: BridgeWeb/src/core/comm-worker/bridge-product-frame-acknowledgement.ts:8-51
  - Plain `executeProductRequest('command', {... method:'POST', signal: abortController.signal})` —
    an ordinary fetch. NOT `keepalive`. NOT `sendBeacon`.
  - It IS awaited: bridge-product-transport.ts:650 awaits the ack inside the frame loop
    (`await this.#acknowledgeMetadataFrame(frame)` — comment at :649 says native pacing advances only
    after the frame is accepted).
  - Self-abort: a `setTimeout` (frame-acknowledgement.ts:28-37) calls `abortController.abort()` after
    `#frameAcknowledgementTimeoutMilliseconds`, which defaults to **5000 ms**
    (bridge-product-transport.ts:238-239).

Execution context [VERIFIED]: the transport is constructed inside the comm worker —
  BridgeWeb/src/core/comm-worker/bridge-comm-worker-entry.ts:224 calls createBridgeProductTransport(...)
  and the worker itself is a dedicated module Worker created from a blob URL at
  BridgeWeb/src/core/comm-worker/bridge-pane-comm-worker-session.ts:461
  (`new Worker(workerScriptBlobUrl, { type: 'module' })`).
So every `stream.frameObserved` POST is a **dedicated-Web-Worker-initiated fetch**, not a main-thread one.

The 5 s self-abort is decisive: a live worker can leave an ack pending for at most ~5 s before
aborting it (which produces `requestfailed`). An entry stuck for 120 s therefore has **no live worker
left to fire its abort timer**.

1.4 Q3 — Playwright behaviour for in-flight requests across a reload [VERIFIED in installed source]
--------------------------------------------------------------------------------

Installed version: playwright 1.61.0 (BridgeWeb/package.json:78 `"playwright": "^1.61.0"`;
BridgeWeb/node_modules/playwright-core/package.json version 1.61.0). 1.61 ships one minified bundle,
BridgeWeb/node_modules/.pnpm/playwright-core@1.61.0/node_modules/playwright-core/lib/coreBundle.js.

(a) No documented guarantee. types.d.ts:1132-1168 describes the *successful* sequence
    ("For a successful response, the sequence of events is request, response and requestfinished")
    and the HTTP-error caveat. It never promises a terminal event for every `request`.

(b) Dedicated-worker requests are tracked by the PAGE's single CRNetworkManager:
    coreBundle.js:37238 — on `Target.attachedToTarget` for a worker,
      `this._crPage._networkManager.addSession(session, this._page.frameManager.frame(parentFrameId ...))`
    so their requests do fire page-level `request`/`requestfinished`/`requestfailed`. (This is why the
    observer works at all, and why :484 passes.)

(c) On worker teardown the network bookkeeping is NOT cleaned up (I read this myself):
      coreBundle.js:37250-37256  _onDetachedFromTarget(event) {
        const workerSession = this._workerSessions.get(event.sessionId);
        if (workerSession) { workerSession.dispose(); this._page.removeWorker(event.sessionId); return; }
        ...
      }
    — it disposes the CDP session and drops the Worker object, and never calls
    `_networkManager.removeSession(...)`. Compare the frame-session and service-worker paths, which DO
    call removeSession (coreBundle.js:37092 and :37630-37633).
    And `removeSession` itself does nothing for pending requests:
      coreBundle.js:35621-35626  removeSession(session) { remove listeners; this._sessions.delete(session); }
    There is no walk of `_requestIdToRequest` to synthesize a terminal event.
    The only place Playwright manually synthesizes a failure on navigation is for the navigation's own
    document request (coreBundle.js:46797-46800) — not sub-resource or worker requests.

    Consequence: once the worker's CDP session is disposed, any `Network.loadingFailed` Chromium might
    still emit for that worker's in-flight requests has nowhere to land, and Playwright provides no
    backstop. Whether the event arrives before the session dies is a protocol-delivery race.

(d) Known issues (context, not proof): microsoft/playwright#9850 ("missing event for aborted requests"
    — same Set-of-in-flight-requests pattern, same gap), #29101 (requestfailed not fired for
    AbortController-cancelled fetch, Firefox). No fix for the worker-detach case is identifiable in 1.61.

(e) `request.frame()` for a worker-initiated request does not throw: Playwright falls back to the
    worker's parent frame captured at attach time (coreBundle.js:35786, :37238). Since Playwright reuses
    the same `Frame` object across a same-frame reload, **`request.frame()` cannot distinguish old- vs
    new-document requests.** `request.serviceWorker()` is null for dedicated workers; the throw at
    coreBundle.js:58084-58087 is service-worker-only.

1.5 MECHANISM FOR A — [VERIFIED mechanism, one HYPOTHESIS step]
--------------------------------------------------------------------------------

VERIFIED chain:
  1. `stream.frameObserved` POSTs are issued from a dedicated Worker, awaited, and self-abort after 5 s.
  2. `observeFrameAcknowledgementQuiescence` adds them on `page.on('request')` and only removes them on
     `requestfinished`/`requestfailed` (quiescence file :24-31). There is no navigation handling.
  3. `createdPage.reload(...)` (journey :692-696) destroys the document and its comm worker.
  4. Playwright 1.61 does not reconcile pending requests when a worker target detaches
     (coreBundle.js:37250-37256; removeSession is a no-op for pending requests at :35621-35626).
  5. The poll at quiescence :36-39 therefore never reaches 0 and times out at 120 s.

HYPOTHESIS (the one unobserved step): that the 1 (run 1) / 4 (run 2) residual entries are specifically
the acks that were in flight at reload, rather than acks from the post-reload document. Supporting
evidence: the count is tiny and stable, matches "how many acks happen to be mid-flight", scales the way
a slower runner would (1 → 4), and any post-reload ack would have been terminated within 5 s by its own
abort timer. Not directly observed because the observer records no per-request detail.

1.6 Q5 — Smallest correct fix for A, and does the server care? [RECOMMENDATION]
--------------------------------------------------------------------------------

Smallest correct fix: give the observer a document epoch and only require quiescence for the current
document. In bridge-viewer-vite-frame-acknowledgement-quiescence.ts, add a main-frame
`framenavigated` handler that drops the previous document's pending entries:

    page.on('framenavigated', (frame) => {
      if (frame !== page.mainFrame()) return;
      pendingRequests.clear();      // or: retire the previous epoch's entries
    });

Why this is sound and not a weakening:
  - Playwright emits `framenavigated` at commit of the new document. No script of the NEW document can
    have run before commit, so nothing issued by the new document can already be in the set.
  - A destroyed document can no longer owe an acknowledgement; waiting on it proves nothing.
  - Filtering by `request.frame()` is NOT available (see 1.4(e)) — the Frame object is reused. The
    navigation event is the only public signal.
  - Prefer the epoch variant over a bare `clear()` if you want the observer to stay able to report a
    leak: keep `Map<Request, epoch>` and poll `size of entries with epoch === currentEpoch`.

Does the dev server end up with an un-acked frame that matters for later assertions? **No.** All the
telemetry assertions that could see pacing state are captured BEFORE the reload:
  - `fileTelemetry` at journey :470-483, `reviewTelemetry` at journey :626-638.
  - The assertions at journey :307-334 (`receiptPendingCount == 0`, `maximumReceiptPendingAge...`, etc.)
    read those pre-reload observations, not a post-reload fetch.
  - The only post-reload measurement is `exactBodyCountAfterReload` (journey :748-773), which is DOM
    body text and does not depend on the old stream's acknowledgement.
  Additionally the old worker's stream is torn down with its document, so the server's per-stream lease
  for it is dead state, not backpressure against the new session.

What would prove the fix:
  1. A focused test of the observer itself (it currently has none): open a page whose worker holds an
     ack against a gated route, call `page.reload()`, assert `wait()` resolves promptly; plus a NEGATIVE
     case where a live-document ack is gated and `wait()` still blocks. Without the negative case the
     fix could silently turn the observer into a no-op.
  2. Re-run the backpressure E2E on the CI runner class and show attempt 1 passing through `file.ready`
     with no 120 s poll (the failure is deterministic-ish on CI: 2/2 attempt-1 runs).

2.2 MECHANISM FOR B — [VERIFIED]
--------------------------------------------------------------------------------

The gate is causally mis-anchored. The demanded projection query is NOT caused by `source.refresh`;
both are caused by `acquireSession`, and their global request sequence numbers race.

Product path, worktree-annotation-surface-client.ts:430-437 (`acquireSession`):
    projectionStore.markSessionDemanded(sessionId)
    execute({kind:'demand.acquire', sessionId})        → sequence 19
    refreshDemandedSession(sessionId)                  → :388-395, executes {kind:'source.refresh'} → 21
    execute({kind:'output.history', sessionId})        → 22
The projection query at 20 is issued by the worker's query controller reacting to the demand, on a
different thread from the main-thread command sequencer. So:
  - lucky interleaving: query lands with a sequence > source.refresh's → gate satisfied → test passes.
  - observed interleaving: query = 20, source.refresh = 21 → 20 <= 21 → the gate rejects the only
    qualifying query that will ever arrive (the source refresh produced no further projection query,
    so `settled` stays false) → 30 s poll → `expected false to be true`.

This is a test-side ordering assumption, not a product delivery failure: the projection the test wanted
(sessionIds [session], expectedMessageCount 1, descriptor present) DID arrive, at sequence 20.

Related prior art (same lane, different test): tmp/debug-workflows/2026-09-17-pr350-ci-flakes/
lane-bridgeweb-flakes.md §3.1 records the same `projection-test-support.ts:187` AssertionError as an
*unhandled* orphan when File-surface `source.refresh` never landed at all. The File-surface
source.refresh ordering has bitten this suite before.

4. SUMMARY
================================================================================

A (attempt 1, both runs) — VERIFIED mechanism, one hypothesis step.
  `observeFrameAcknowledgementQuiescence` leaks pending entries across `page.reload()`. The acks are
  dedicated-Worker fetches; Playwright 1.61 does not reconcile a worker's in-flight requests when the
  worker target detaches (coreBundle.js:37250-37256 never calls removeSession; removeSession at
  :35621-35626 is a no-op for pending requests), so no `requestfinished`/`requestfailed` ever arrives.
  The client's own 5 s abort (frame-acknowledgement.ts:28-37, default 5000 at transport.ts:239) cannot
  fire because its worker is gone. First wait (:484, no preceding reload) passes; second (:706, right
  after reload) times out. Fix: retire the previous document's entries on main-frame `framenavigated`.
  No server-side consequence for the test's later assertions (all telemetry assertions are pre-reload).

B (retry, both runs) — VERIFIED mechanism.
