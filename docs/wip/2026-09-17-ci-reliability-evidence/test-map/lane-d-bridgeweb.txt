0. THE ONE FACT THAT REFRAMES THIS WHOLE LANE
================================================================================

The repo already owns the mechanism this lane needs, and is not using it for E2E.

  BridgeWeb/vitest.browser.config.ts:41-47 declares a vitest TAG:
      tags: [{ description: 'Scale-bound browser workloads run outside the per-commit
               correctness lane.', name: 'stress' }]
  BridgeWeb/package.json:25-26 splits that lane by tag:
      test:browser:integration  -> --tags-filter=!stress
      test:browser:stress       -> --tags-filter=stress
  .github/workflows/benchmarks.yml:56-57 runs `mise run test:bridge-web:stress` post-merge/nightly,
  under its own comment at :7-8:
      "Nightly run keeps the timing policies (benchmark suites, BridgeWeb stress, large lane)
       exercised without putting wall-clock gates in the pull-request lanes."

  BridgeWeb/vitest.e2e.config.ts has NO `tags` key at all (whole file is 19 lines; :3-18).
  The E2E stress split is done by FILE PATH in BridgeWeb/package.json:30-32:
      test:e2e:prepared         = test:e2e:prepared:stress && test:e2e:prepared:ordinary
      test:e2e:prepared:stress  = ...run tests/e2e/bridge-viewer-vite-annotation-backpressure.e2e.test.ts
  and .github/workflows/ci.yml:255 runs `test:e2e:prepared` — BOTH halves — on the PR gate.

So the 600-second, 1,699-item, long-task-counting backpressure journey is precisely the
"wall-clock gate in the pull-request lane" that the benchmarks workflow's own comment says
should not exist. The destination lane exists, the tag mechanism exists, and the E2E config
is the only one that never adopted it. Nothing new has to be invented to move the (P) claims.

Corroborating admission in the config itself — BridgeWeb/vitest.e2e.config.ts:15-17:
      // Browser repaint/scroll journeys are timing-sensitive on CI runners; one retry
      // keeps every assertion while tolerating the known intermittent.
      retry: 1,
`retry: 1` is applied to EVERY e2e test, not just the timing-sensitive ones. It doubles a
993-second lane and, per the evidence report, produces two differently-shaped records for one
defect. It is the current answer to speed dependence.

SPEED DEPENDENCE — the precise mechanisms, each verified in code:

  SD-1. `longTaskCountDelta == 0` (journey.ts:285-298). The value is the count of browser long tasks
        (>=50 ms, by spec) whose interval overlaps [mainBegin, mainCommit]
        (annotation-catalog-performance.ts:335-346). On a contended 3-vCPU runner the SAME correct
        program produces long tasks; on an idle laptop it produces none. The evidence report records
        11 and 17 long tasks on CI against 0 locally for the identical code
        (lane-bridgeweb-backpressure-e2e.md section 6.3). This assertion's verdict is a function of
        the runner, not of the program. It is the single clearest example of the class the brief
        exists to eliminate.

  SD-2. Three age assertions against `renderReceiptLeaseMilliseconds = 5_000` (journey.ts:67, asserted
        at :324-332): maximumReceiptPendingAgeMilliseconds, maximumPublicationAgeMilliseconds,
        maximumWorkerQueueWaitMilliseconds. Each is a real wall-clock duration measured inside the
        app under load. A slower machine raises all three while the program logic is unchanged.
        Worse, each is a MAX over every sample still in the telemetry ring
        (backpressure-telemetry.ts:205-216), so one slow moment anywhere in the ~200-second journey
        fails the whole test, and the message does not say which moment.

  SD-3. `reviewTelemetry.highWaterMark <= 12` (journey.ts:316) and
        `receiptHighWaterMark <= 6_144` (:323). These are genuine flow-control bounds (good claims),
        but as measured here the observed high-water mark depends on how fast the consumer drains:
        on a fast machine the ledger may never reach 12. The assertion is one-sided (<=), so it does
        not flake — but it also cannot fail on a fast machine, which means the PR gate is not
        actually exercising the bound it names. Proof strength here is machine-dependent in the
        other direction.

  SD-4. `settleBrowserFrames(page, 2)` (annotation-catalog-performance.ts:432-441) — two
        requestAnimationFrame ticks used as "the UI has settled". Used at journey.ts:576, :657 and
        inside frame-acknowledgement-quiescence.ts:40. Two frames is a guess about React's commit
        schedule, not a signal from React. Under load the relevant commit lands on frame 3.

  SD-5. `expect(bootstrapRequestCount).toBe(1)` at journey.ts:509 and `.toBe(2)` at :705, :723.
        This is a strong and valuable claim (mode switching must reuse the live session; only a
        document navigation may re-bootstrap). But it is read at a point in time chosen by the
        preceding wait; a late third bootstrap arriving after :723 is never seen. It is a negative
        assertion over an open window. It cannot flake — it can silently pass while wrong.

  SD-6 (HYPOTHESIS, with a named mechanism). `observeSelectedItemApplies(createdPage)` is created at
        journey.ts:441 and INSTALLED at :530, which monkey-patches the production prototype:
        `BridgeCodeViewController.prototype.applyItemUpdate` (selected-item-apply-observation.ts:26-39),
        wrapping every item update for the rest of the journey, and for the selected item capturing
        `new Error().stack` (:33) on each apply. Its output global `__bridgeSelectedItemApplies` is
        NEVER READ by this journey — grep shows readers only at save-journey.ts:392,
        annotation-reply-observation.ts:181 and reply-failure-observation.ts:55. So this journey pays
        a production-prototype patch plus per-apply stack capture during the exact window in which it
        then asserts zero long tasks, and discards the result. I have not measured the cost; the
        mechanism is verified, the magnitude is not.

WHEN IT FAILS YOU SEE: for the timing class, a good message — journey.ts:287-297 serialises
      continuousBounds, mainStagingSamples, matchedEntries and the full observation. Someone was
      already narrowing this (the evidence report notes `matchedEntries` post-dates the CI records).
      For everything else you see `Bounded E2E operation timed out.` (journey.ts:219) plus a
      milestone label. The label is frequently WRONG: `runAnnotationSaveJourney` at :257-261 is not
      wrapped in a milestone, so a failure anywhere inside that 928-line journey reports
      `server.ready`. Five of eight CI failures in the evidence report carry that misleading label.
      Additionally the diagnostic fetch at :339-341 has no timeout, and runs BEFORE the diagnostic is
      snapshotted at :349 — so `currentElapsedMilliseconds` includes however long that hung.

VALUE: the durability half is real and is not proved anywhere cheaper — six distinct annotations
      surviving a reload at 1,699-item scale, through a real Swift backend and real SQLite, is a
      journey no unit test can make. The measurement half is not a test.

      Drop the 2,000-message catalog clone (journey.ts:262-268) from this journey: the catalog
      windowing claims it exists to feed all move to (C), and cloning 2,000 rows through

  (B) THE MEASUREMENT LANE — moves to the post-merge workflow that already exists.
      Moves: :285 longTaskCountDelta === 0, :324/:327/:330 the three 5,000 ms age bounds,
             and :316/:323 the high-water bounds as REPORTED TRENDS rather than PR booleans.
      stimulus: unchanged — the same journey, the same 1,699 items, the same catalog clone.
      Mechanism, and it is all pre-existing:

        2. tag the backpressure test `stress`;
        3. change package.json:30 `test:e2e:prepared` to `--tags-filter=!stress` and add an
           `test:e2e:prepared:stress` step to .github/workflows/benchmarks.yml alongside the

      what it should compare: the same four numbers against the previous main-branch run on the

      not "this number was above 0 once on a contended VM". That comparison is exactly what
      benchmarks.yml:7-8 says the nightly lane is for.
      NOTE: `longTaskCountDelta == 0` should NOT be relaxed to a threshold. As a trend on a fixed
      runner class it is a meaningful regression detector. It is only meaningless as a PR boolean.

      unit level without faking the very boundary under test.
      BUT their current stimulus is wrong for the claim: they are asserted after a happy-path run
      and merely observe that the bad fetch did not happen. The forceable version is to make the
      completed session the MOST TEMPTING one to fetch — which the fixture already does by cloning
      2,000 messages into it (annotation-catalog-performance.ts:60-147) — and then assert over a
      CLOSED window rather than a point in time.

      installs `projectionRouteHandler`, which HOLDS every `contentKind === 'annotation.projection'`

Across the observers there is one rule that sorts every case cleanly:

  A test-side reconstruction used as a DIAGNOSTIC is good engineering.
  The same reconstruction used as an ORACLE is a second implementation of the system,

  Diagnostic-only, keep: observeBrowserRuntimeDiagnostics (3.4), installReviewRenderObservation (3.5).
  Oracle, and wrong:     observeFrameAcknowledgementQuiescence (3.1),

PATTERNS SEEN MORE THAN ONCE
================================================================================
1. Deadline-poll on owner-rendered DOM state via `page.waitForFunction`/`.waitFor`/`expect.poll` — the
   dominant wait mechanism across every test in this batch (>25 call sites across all 6 records). This is
   largely the *correct* pattern per the brief's own bar (a poll with a deadline that IS the completion
   signal), not the flaky "poll a reconstructed side-channel" anti-pattern.
2. Test-side counters/sets reconstructing wire traffic instead of asking the product's own owner state:
   `rejectedReceiptCount`/`rejectedReplacementCount` (Records 1,2), `proxy.snapshot()`'s
   `metadataRequestCount`/`activeMetadataResponses` (Record 3), `firstBootstrapCount` (Record 5) — 4
   distinct occurrences. Three of these (Record 1's and 2's fault counters) are legitimate because they
   count the test's *own* injected fault, not product state; the other two (Record 3's proxy snapshot,
   Record 5's bootstrap count) are asking a side channel for something an owner API could answer more
   directly (see B1-B5 above).
3. Failure-message diagnostics inconsistency: two tests thread an explicit `phase` breadcrumb through their
   catch block (worker-recovery #1, annotation-edit-reopen) and four do not (worker-recovery #2, stream-
   recovery, sustained-file-refresh, tab-ownership) — the two with `phase` are meaningfully easier to
   triage from a CI failure than the four without.
4. Duplicate coverage between an E2E worker/stream-recovery journey and an existing deterministic
   scripted-harness unit test that proves the same decision without a browser: worker-recovery #1 vs
   bridge-main-review-publication-recovery.unit.test.ts:15-61 (confirmed via the wire-method mapping at
   bridge-comm-worker-runtime-command-routing.ts:92-95); stream-recovery's 'disconnected' case vs
   bridge-product-transport-reconnect.unit.test.ts:24-90.
5. Every single test in this batch pays the same full-stack setup/teardown cost (real Swift backend
   subprocess + real Vite child process + real Chromium + `runAllOwnedCleanupOperations`) — not itself a
   flake risk, but it means the aggregate CI tax of six independent full-stack spins is a shared cost
   regardless of how "thin" any individual claim is; several of the split-and-push-down recommendations
   above reduce that tax as a side effect.

Q4. Is the A3 failure (act() warning from a deferred base-ui flushSync, turned into a hard
    failure by the global guard) an oracle problem, a wait problem, or a real product
    finding?

  It is a WAIT problem in the test, not an oracle problem and not (on current evidence) a
  product-behavior defect visible to a real user. Reasoning from the code, not the report:
  - The guard's oracle — "no console.error escapes an `act()` scope for the life of this
    browser run" — is a legitimate, deliberately strict proof gate
    (tests/vitest-browser-setup.ts:19-28 pins `IS_REACT_ACT_ENVIRONMENT=true` for exactly
    this reason, per its own comment; :60-68 converts every non-allowlisted console.error into
    a hard failure). Weakening the oracle (loosening or allowlisting the message) is
    explicitly the wrong move — the evidence report already says not to allowlist a second
    base-ui flushSync symptom, and I independently verified the allowlist already contains
    exactly one such entry (:30-32, `'flushSync was called from inside a lifecycle method'`)
    — adding a second converts the gate into decoration.
  - The actual mechanism is a WAIT gap: base-ui's CollapsiblePanel schedules its *closing* and
    re-armed dimension updates from two paths outside any React `act()` the test controls —
    a rAF-deferred `runOnceCloseAnimationsFinish`
    (`@base-ui/react/collapsible/panel/useCollapsiblePanel.js`, closing effect at lines
    ~228-263, `AnimationFrame.request(() => runOnceCloseAnimationsFinish(handleComplete,
    ...))`), built from `useAnimationsFinished(panelRef, false, false)` (verified at
    useCollapsiblePanel.js:65 — `treatAbortedAsFinished=false`). Inside
    `useAnimationsFinished` (BridgeWeb/node_modules/@base-ui/react/internals
    /useAnimationsFinished.js:37-53), when `treatAbortedAsFinished` is false and an animation
    aborts, `exec()` re-arms itself (`.catch(() => { ...; exec(); })`) and the eventual
    completion calls `ReactDOM.flushSync(fnToExecute)` (:36-38) whenever that later frame
    lands — which can be after `settleThreadMotion`'s own MutationObserver has already
    resolved (it only watches the OPENING transition,
    worktree-annotation-thread.browser.test-support.tsx:190-208) and after the test's `await
    page.screenshot(...)` (test:592) has yielded to the browser with no `act()` scope open.
  - This is exactly the same class of gap as Record 1's unbounded animation await — the test
    (and the shared helper) joins the transition it started, but base-ui's OWN internal
    completion machinery can still fire a later, uncoordinated `flushSync` that the test never
    opens an `act()` scope for. That is a test-harness wait gap, not a defect in the product's
    observable behavior: a real user does not see or care about `act()` warnings, and nothing
    in the traced mechanism shows stale or wrong DOM — only an unguarded late commit.
  - It is explicitly NOT provably an oracle-attribution problem in the sense of "wrong test
    blamed" being fixable by better logging alone, though the report is right that the guard's
    current attribution is weak: `browserFailureMessages` is reset in `beforeEach` (:40) and
    drained in `afterEach` (:53) with no stack captured at the `console.error` call site
    (:62-68), so which test the warning "belongs to" is only ever "whichever test was current"
    — that is a secondary, fixable diagnostics gap (cheap: capture a stack at the call site),
    separate from the primary wait-gap fix (join the closing/re-armed path, or don't leave an
    act()-less yield across it).
  CONFIDENCE: high on "wait problem, not oracle problem, no product-visible defect shown by
  this evidence" (grounded directly in the base-ui source paths cited above, read in this
  checkout, not paraphrased from the report). Medium on "which exact call in THIS test run
  fired late" — the current guard genuinely cannot say (verified: no stack, reset in
  beforeEach, drained in afterEach), so that residual is honestly unresolved, matching the
  evidence report's own UNVERIFIED note.

3. "Bare expect.poll/expect.element with no explicit timeout" (count: 8 across the two
   records, verified line-by-line under Q3) — every one of them silently depends on a vitest
   default (1000ms/50ms) that no BridgeWeb config file sets, confirmed absent from all four
   vitest.*.config.ts files.
4. "Base-ui's own transition-complete callback exists but isn't wired to the test" (count: 2
   — Drawer's onOpenChangeComplete for Record 1, CollapsiblePanel's onComplete/

   re-approximate a signal the underlying library already computes and could hand out
   directly if the production component forwarded it.

================================================================================
WHAT SURPRISED ME
================================================================================

- The evidence report frames A1 and A2 as two separate failure families, but they are
  literally the same test body (worktree-annotation-share-surface.browser.test.tsx:216-271)
  failing at two different points on two different CI runs — the file was edited between
  those runs (suite name changed from "Share comments…" to "Annotations…", per the report's
  own §2.2 note), so mapping them separately would have double-counted one test's design
  problem as two.
- The New/Pending/comment-count ORDERING half of A3's claim turned out to require no wait
  design at all once traced to its source: it is unconditional JSX element order
  (compact-thread.tsx:566-591), not a runtime decision, so no amount of test-design cleverness
  changes anything about it — the entire "ordering" half of the claim reduces to "did someone
  edit the JSX," which the existing browser assertion (or a trivial snapshot) already catches
  for free.
- Base-ui ships the exact "owner-reported settled" signal this whole family of tests is
  missing — `onOpenChangeComplete` on both Drawer and (via `useAnimationsFinished`'s
  `onComplete`) CollapsiblePanel — and this app's production wrapper components
  (WorktreeAnnotationSharePanelControl, and by extension whatever renders
  WorktreeAnnotationCompactThread's collapsible) do not forward it anywhere. Every hand-rolled
  MutationObserver/animation-await in this package is reimplementing, less reliably, a
  callback the library already computes internally.
