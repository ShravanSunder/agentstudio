  The five bare loops have NO assertion that the loop succeeded. If the budget expires, execution simply falls

  `#expect(capture.fullCaptureCount == 1)` at :162 can pass because the sort-direction invalidation has not

SPEED DEPENDENCE: the wait at :165 is the one the report blames, and the mechanism is real — I re-derived it.
  `observationRegistration.paneIDs` is written INSIDE a capture, by `installObservationTokens()`
  (Sources/AgentStudio/Features/RepoExplorer/RepoExplorerProjectionAdapter+InputLifecycle.swift:103-119,
  the write is at :109). It is a mid-pipeline effect, not a settle signal. Between an observed write and that
  effect there are two MainActor task hops, each with its own explicit yield:
    hop 1 — `withObservationTracking { … } onChange: { Task { @MainActor in await Task.yield(); … } }`
            (:132-139, the enqueue is at :161)
    hop 2 — `enqueueInvalidation` → `invalidationTask = Task { @MainActor in await Task.yield(); …;
            processPendingInvalidation() }` (:166-176)
  So the coalescing window for this adapter is literally "whatever arrives before the single live
  invalidationTask resumes from its one Task.yield()". It is not a debounce and not a deadline — it is a race
  with the MainActor job queue. Sampling a count baseline on `paneIDs` (a mid-capture effect) and then
  asserting the count did not grow can be defeated by any invalidation still sitting at hop 1 or hop 2.
  The :187 loop is worse: a negative assertion at :188 whose entire proof is "100 turns elapsed". On a fast
  machine those 100 turns may be microseconds.

              - for the hidden case at :188, the strong oracle is already on the next two lines up:

  wait:     the settle predicate already exists in this file, spelled out by the sibling test

  keeps:    the real-NSWindow materialization check (:179) and the hidden-demand structural assertions.

      count's clothes.
  The cure is uniform: a negative assertion needs a MORE positive barrier than a positive one, because there
  is no event to wait for. Either settle the owner first, or convert the claim to a positive statement about
  owner state (a future deadline, an empty token set) that is true at a defined instant.

P2 — BARE TURN LOOP WITH NO FAILURE (7 instances, all in RepoExplorer: :143, :149, :153, :159, :187, :225, :242).
  `for _ in 0..<N where <not done> { await Task.yield() }` with no assertion that the loop succeeded.
  Budget exhaustion falls through into the next `#expect`. Strictly worse than a flake: it turns a timeout
  into a silent pass. Note the contrast in PaneTabViewControllerLaunchRestoreTests, whose waitUntil returns
  Bool and whose doc-comment at :400-401 explicitly requires every call site to `#expect` it — and all four
  do. Same mechanism, opposite hygiene. The RepoExplorer loops should become assertEventuallyMain today,
  independent of any seam decision.

P3 — A COMPLETION SIGNAL EXISTS AND IS DISCARDED (3 instances).
    - BackgroundFactApplyGovernor returns a real per-fact Acknowledgement (:13-20, resolved `.applied` at :248
      after the MainActor commit, `.superseded` at :180); WorkspaceCacheCoordinator throws it away three
      times: `_ = governor.enqueue(...)` at :293, :305, :348.
    - TerminalActivationScheduler has a proper waiter list for `activate()` (:166-210) and none for the
      supplemental drain (:285-294) — the only path the four launch-restore tests exercise.
    - BridgePaneRefreshAdmissionCoordinator computes everything needed for idleness in completeRefreshPass
      (:386-397) and exposes only a poll-shaped diagnosticSnapshot (:155-160), while its sibling
      BridgePaneWorktreeRefreshDriver already ships a real awaitable (awaitRetiringFileOperations, :99-106).
  In every case the owner knows when it is done and declines to say so. Tests then reconstruct the answer by
  polling. This is the single highest-leverage production change available to this lane.

P4 — THE POLL-SHAPED TEST SEAM AS AN ANSWER TO A MISSING BARRIER (2 instances).
    - BackgroundFactApplyGovernor.supersededSinceLastDrainCount (:206-213). Its doc-comment says it exists so
      "tests can wait for an actual coalescing invariant". Someone already hit this exact problem and shipped
      a counter to poll instead of a completion to await.
    - BridgeReviewContentLoaderCache.diagnosticSnapshot (:51-55) reports in-flight KEY count, which is not the
      quantity any test needs (attached WAITER count).
  When the next person adds an observability seam for a test, the question to ask is "can this be awaited?"
  not "can this be read?".

P5 — THE ORACLE IS A FAKE'S POLICY, NOT A PRODUCT INVARIANT (1 clear instance, called out here because of its
  blast radius). PaneTabViewControllerLaunchRestoreTests asserts `createSurface` was called exactly twice
  against a manager that always fails (:885). The file's own header (:11-17) admits this proves an
  attempt/retry policy, not a created surface. Four tests depend on the literal 2.

P6 — MIXED CLOCK INSIDE ONE ARITHMETIC EXPRESSION (1 instance, high consequence). The Git projector adds a
  real-ContinuousClock duty (+AvailableStatus.swift:13-14 → +DeadlineRefresh.swift:538) to a virtual
  TestPushClock instant inside `max(lastStart + cadence, lastCompletion + dutyGap)`
  (+DeadlineRefresh.swift:496-499). The test recomputes the same max, so it never fails from this — it
  silently stops exercising its own claim under load.


================================================================================
(3) WHAT SURPRISED ME
================================================================================

S1 — Four of the seven tests were already fixed, and the fixes are good. `visibleTierWaitUntil` is gone,
  `waitForStartedComparisonCount` is now continuation-backed, the RepoExplorer two-write coalescing assumption
  is gone, and TestPushClock has grown a full family of real barriers (waitForPendingSleepCount exactly/
  atLeast/fromGeneration/generation, TestPushClock.swift:209-224). Anyone planning remediation off the
  evidence report alone will spend slots on already-closed work. The GitWorkingDirectoryProjectorVisibleTier
  file is now the best in-repo example of how these waits should look, and the other lanes should copy from it.

S2 — The `consumedCount == 3` barrier in test 1 is SOUND, contrary to the natural reading of "EventBus records
  consumption when an item is pulled, before it is handled". It works only because the coordinator's loop body
  for a coalescable envelope is synchronous all the way into the governor's lock. That is a load-bearing fact
  nobody wrote down next to the barrier — the test comment at :446-448 asserts the conclusion but not the
  synchronous-enqueue premise it depends on. If someone ever makes enqueueCoalescedEnrichment async, this
  barrier silently becomes a lie and the test becomes flaky again with no visible cause. Worth a comment at
  WorkspaceCacheCoordinator.swift:157.

S3 — `await coordinator.shutdown()` at WorkspaceCacheCoordinatorTests.swift:484 is ALREADY a complete,
  deterministic barrier for every pending fact (shutdown → await consumeTask.value → governor.shutdown →
  flushAllPendingFacts). The test polls for the applied value four lines earlier and then does the
  deterministic thing anyway. The flaky wait is, in a real sense, load-bearing only for distinguishing
  "the tick applied it" from "shutdown flushed it" — which is worth keeping, but nobody appears to have
  noticed that is the only thing it buys.

S4 — There are TWO untracked tasks between the launch-restore tests' stimulus and their oracle, not one. The
  scheduler's supplemental drain (:285) gets all the attention, but
  `schedulePreparedTerminalGeometryReevaluation` spawns its own fire-and-forget Task first
  (WorkspaceSurfaceCoordinator+ViewLifecycle.swift:718-724). Adding a scheduler barrier alone will reduce the
  flake without eliminating it, and whoever takes that work should be told so up front rather than discovering
  it after the fix lands.

S5 — The evidence report's mixed-clock note is materially wrong in the direction that matters. It says the
  projector's duty and admission timestamps run on a real clock; in fact `lastAutomaticStartAt`,
  `lastAutomaticCompletionAt`, and `automaticRefreshDeadline` are all on the INJECTED clock
  (+DeadlineRefresh.swift:476, :524-525, :535-537, via GitWorkingDirectoryProjector.swift:147). Only
  `lastAutomaticDuty` is real. So the file is far closer to deterministic than reported — one field away,
  not four — and the remediation is correspondingly smaller than it looks.

S6 — The decisive diagnostic for the launch-restore family already exists and is never captured.
  `TerminalActivationScheduler.memberState(for:)` (:296-299) and `diagnostics()` including yieldCount
  (:301-307) would separate poll-starvation from an ordering miss in a single failing run. Adding them to the
  failure message costs nothing, requires no design decision, and should happen before anyone argues about
  which root cause it is. Four tests have been failing together with a message that cannot distinguish two
  completely different bugs.
