    - FSEvents: `captureActivityBarrier()` is `package`, `@concurrent nonisolated`, and used by six sibling
      suites; this fixture acknowledges the fences it sees and throws them away (support :97-100, :348-351).
    - Dev-host: `metadataRetirementBarriersForReload()` + `BridgeProductProducerRetirementBarrier.wait()` are
      exactly what the host itself awaits (BridgeDevelopmentProductHost.swift:860-868); the test awaits
      neither.


================================================================================
(3) WHAT SURPRISED ME

S1. The strongest finding in this lane is a PRODUCTION ordering bug, not a test bug.
    `GitWorkingDirectoryProjector+RefreshAttribution.swift:194-195` announces the settlement and THEN records
    the telemetry. Because `resolve` hands off across executors (RepositoryFactSourceUpdate.swift:56-73), ANY
    consumer — not just this test — can observe "settled" in a state where the settlement is not yet recorded.
    I went looking for a test-side barrier and found that the right fix is a two-line swap in production that
    makes the contract stronger for everyone. The flaky test was reporting a real, if small, defect. That is
    the opposite of this lane's usual story and it is worth saying out loud before the remediation work starts
    treating every red test as a test-quality problem.

S2. The FSEvents fixture is not missing a barrier; it is ignoring one it can already see.
    `collectFullGitRefreshBatches` and `collectLocalSentinelBatches` both pattern-match
    `.activityProcessingFence`, acknowledge it, and `continue` (support :97-100, :348-351). The fence flows
    through the fixture's own hands on every run. Meanwhile `captureActivityBarrier()` — which flushes both
    stream families with `FSEventStreamFlushSync` AND awaits a fence AND re-validates topology — sits one
    `private` keyword away, used by six sibling suites in the same directory. The evidence report framed this
    as "the fixture never enqueues a fence", which understates it: the complete, correct, production-owned
    barrier was already built, already adopted next door, and simply not reached for here.

S3. Two of the eight tests are provably redundant or near-redundant with a BETTER sibling in the same file.
    `activeInAppPriorityWinsQueueOrder` is a strict subset of `priorityOrderingFocusedThenActiveThenSidebar`
    — and the sibling is not only stronger but explicitly documents, in a code comment (:506), the exact
    stimulus discipline whose absence makes the weaker test flaky. Nobody went back and fixed the older one.
    Test suites accrete this way; a flake inventory is a good moment to prune.

S4. `BridgePaneProductFileBootstrapSuspensionTests` achieves 100% determinism with ZERO test-only production
    hooks. Every seam it uses is a defaulted constructor parameter or a protocol that production itself
    consumes (BridgePaneProductFileMetadataSource.swift:80, :83; BridgePaneController+Bootstrap.swift:599).
    The repo rule "do not add new `#if DEBUG` test hooks in production files" is often argued as a cost;
    here it is demonstrably free, and the resulting seam is BETTER than a debug hook because production
    exercises it, so it cannot rot.

S5. The one test in this lane whose failure message was genuinely good — the dev-host replay's typed
    `sessionAlreadyOpen` — is also the one most likely to be misdiagnosed, because the message describes a
    legitimate product refusal. A well-named error is not the same as a well-attributed failure. Whatever the
    remediation does about messages, "the refusal is typed" should not be mistaken for "the reader will know
    it was a self-inflicted race".
